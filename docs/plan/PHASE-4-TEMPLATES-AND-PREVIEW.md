## 2. Part A — The site generator (`src/export/`)

### 2.1 API (lock this surface)

```ts
// src/export/generator.ts
import type { Project } from '@/types/blocks';

export interface GeneratedSite { html: string; css: string; js: string; }

export interface GenerateOptions {
  /** Maps a stored relative path ("assets/foo.png") to a display URL. */
  resolveAsset: (relative: string) => string;
}

export function generateSite(project: Project, opts: GenerateOptions): GeneratedSite;
export function generateHtml(project: Project, opts: GenerateOptions): string;
export function generateCss(project: Project): string;
export function generateJs(): string;
```

> ⚠️ **The #1 preview gotcha, solved here:** a `srcdoc` iframe has no usable base URL, so relative image paths (`assets/foo.png`) won't load in preview. The `resolveAsset` callback is the fix, and it's why the option exists:
> - **Preview:** `resolveAsset = (rel) => convertFileSrc(projectDir + '/' + rel)` (asset protocol from Phase 1)
> - **Export:** `resolveAsset = (rel) => rel` (relative paths — required so the exported site works over `file://` and any host)

Three files, each ~100–200 lines of pure functions:

### 2.2 `generateHtml` — semantic, readable output

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>My Site</title>                        <!-- = project name (v1 has no SEO panel — locked) -->
  <link rel="stylesheet" href="styles.css">
  <link href="https://fonts.googleapis.com/css2?family=Inter:wght@400;500;600;700&display=swap" rel="stylesheet">
</head>
<body>
  <!-- Hero -->
  <section class="lw-hero b-abc123">
    <div class="lw-hero__inner">
      <h2 class="lw-heading b-def456">We bake bread daily</h2>
      <a class="lw-btn b-xyz789" href="#">Get started</a>
    </div>
  </div>
  <script src="script.js"></script>
</body>
</html>
```

- [ ] Each block gets its Layer-1 class **plus `b-<id>`** (the hook for its resolved style rule).
- [ ] Emit `<link>` tags only for Google fonts actually used in the tree (collect via `walk`).
- [ ] Output is **pretty-printed** (2-space indent) with section comments — users will read their exported code; it must feel hand-written.
- [ ] Reuse **one recursive `renderBlock(block): string`** — mirror of the canvas `BlockRenderer`, same structure as the Phase-3 spec sheets.

### 2.3 `generateCss` — the three layers, flattened

```css
/* styles.css — generated by LocalWeb */
/* 1. Reset …  2. Base blocks (verbatim src/styles/blocks.css content) … */
/* 3. User overrides — resolved via the SAME resolveStyles() as the canvas */
.b-abc123 { font-family: "Playfair Display", Georgia, serif; padding: 96px; background-color: #0f172a; }
```

- [ ] Import the **text of `blocks.css` at build time** (Vite `?raw` import: `import blocksCss from '@/styles/blocks.css?raw'`) so it can be embedded — one source of truth, zero duplication.
- [ ] Serialize the result of `resolveStyles(block)` (camelCase → kebab-case) into `.b-<id> { … }` rules. Omit empty rules.

### 2.4 `generateJs` — tiny, vanilla, commented (~40 lines)

- [ ] **Mobile nav toggle:** hamburger button flips `aria-expanded` + a `.lw-navbar__open` class (paired with a few lines in `blocks.css` — already written in Phase 3's media query).
- [ ] **Smooth anchor scroll** for `#` links (`scrollIntoView({ behavior: 'smooth' })`).
- [ ] No dependencies, no modules, works over `file://` (locked: plain HTML/CSS/JS only).

### 2.5 Determinism + golden test (cheap insurance)

- [ ] Same tree → **byte-identical output** (no timestamps in generated files).
- [ ] Add a vitest golden-file test: a fixture tree → compare `generateSite` output against a stored snapshot. Every future block change that breaks the generator fails tests before it breaks users. (Ask AI: *"vitest snapshot test for generateSite"* — 20 minutes of work.)

## 3. Part B — Preview mode

### 3.1 UX (matches the locked editor layout)

- [ ] Top bar **Edit ⇄ Preview** toggle (icon buttons: `Pencil` / `Eye`).
- [ ] Entering preview: left/right panels slide away; canvas becomes a **device frame** with a device switcher (icons: monitor / tablet / smartphone) + width label.
- [ ] Exit returns to edit with selection intact.

### 3.2 Implementation

```tsx
// src/components/canvas/PreviewFrame.tsx (sketch)
const DEVICES = { desktop: 1280, tablet: 768, mobile: 390 } as const;

// regenerate on store change, debounced ~250ms
const site = useMemo(() => generateSite(project, { resolveAsset }), [debouncedTree]);

<iframe
  srcDoc={site.html}
  sandbox="allow-scripts"
  style={{ width: DEVICES[device], height: '100%', transform: `scale(${fit})`, transformOrigin: 'top center' }}
/>
```

- [ ] `<style>` and `<script>` are inlined into the `srcDoc` document (preview has no folder) — generator emits `html` referencing `styles.css`/`script.js`; the preview wrapper injects `site.css`/`site.js` in their place. Keep this logic in one small function.
- [ ] **Scale-to-fit:** if the device width exceeds available canvas width, scale the iframe down via CSS `transform: scale()` (fit = availableWidth / deviceWidth). Show the zoom % subtly in the device bar.
- [ ] Debounced live updates: typing in edit mode then toggling preview always shows fresh output; no file writes, no page reloads.
- [ ] `sandbox="allow-scripts"` is enough for the nav toggle. If anything misbehaves, ask AI before loosening it — this is the app's own generated content, so the risk is low, but keep it as tight as works.

### 3.3 Why an iframe at all? (so you never doubt the design)

The canvas is React components for *editability*; the preview is the *generator's actual output*. Preview = a dress rehearsal for export. If it looks right in preview, it exports right. This is the payoff of the Phase-3 resolver architecture.

## 4. Part C — Templates

### 4.1 Architecture: templates are **data, not code**

```ts
// src/templates/types.ts
export interface TemplateDef {
  id: 'portfolio' | 'business' | 'restaurant';
  name: string;               // "Portfolio"
  tagline: string;            // one-liner for the card
  thumbnail: string;          // inline SVG wireframe (see 4.4)
  /** Creates a full starter project tree — typed BlockNode[] so the compiler enforces the model */
  create(name: string): { tree: BlockNode[]; assets: string[]; /* bundled sample images to copy */ };
}
// src/templates/index.ts — registry consumed by the chooser
export const TEMPLATES: TemplateDef[] = [portfolio, business, restaurant];
```

- [ ] A template is a factory returning **typed `BlockNode[]`** — same model, same tokens, no special cases. `createBlock()` from the Phase-2 registry builds each node (bypassing drag-drop entirely), so template trees are guaranteed valid.
- [ ] **Sample images** ship inside the app (`public/sample-assets/`) and are **copied into the project's `assets/`** on template use, with proper `AssetRecord`s — exported sites are self-contained, no app dependency.
- [ ] Write **real, believable copy** in templates — never lorem ipsum. Users judge the whole product by the first 10 seconds of a template.

### 4.2 The three templates (locked list)

| | **Portfolio** | **Business Landing** | **Restaurant / Local** |
|---|---|---|---|
| Who it's for | students, freelancers | small businesses, agencies | restaurants & local shops |
| Tree (10–14 blocks) | hero (name + role + CTA) · 2–3 image work samples · heading + text "About me" · text + button "Contact me" · footer | navbar · hero (headline + subtext + CTA button) · heading + text ×3 (services) · image · text + button CTA · footer | navbar · hero with **background image** · heading + text (menu highlights) · image · heading + text (hours & address) · link (map/phone) · footer |
| Fonts | Playfair headings + Inter body | Poppins headings + Inter body | Playfair headings + system body |
| Palette | warm neutrals, black accents | blue `#2563eb` + slate neutrals | terracotta `#c2410c` + cream |
| Every block used at least once? | ✅ | ✅ | ✅ (templates double as block demos) |

### 4.3 Start screen upgrade (replaces the Phase-2 minimal screen)

- [ ] Three **template cards** (thumbnail, name, tagline, "Use template" button) + **"Blank project"** card + "Open existing…" + recents list.
- [ ] Flow: pick template → project name + folder dialog → copy sample assets → hydrate store → editor opens with a complete page.
- [ ] Choosing a template must feel instant: the moment of "wow" that carries the 10-minute success metric.

### 4.4 Thumbnails — hand-made SVG wireframes

- [ ] One small inline SVG per template (60–90 minutes total with AI help): gray boxes representing hero/sections/footer with the template's palette and font vibe. Static, reliable, fast.
- [ ] *(Stretch, optional):* live mini-renders (iframe at 280px). Only if the SVGs feel insufficient — ship SVGs first.

## 5. How to verify (Phase 4 exit test)

1. Launch → start screen shows **3 template cards + Blank + Open + recents**
2. Click **Business Landing** → name it, pick folder → editor opens with a full, realistic page
3. Toggle **Preview** → panels slide away, device bar appears, site renders in iframe
4. Cycle **Desktop (1280) → Tablet (768) → Mobile (390)** → layout reflows at each width; **no horizontal scrolling** at mobile
5. In mobile preview, tap the **hamburger** → nav links expand (script.js works in preview)
6. Exit preview → edit the hero headline → re-enter preview → **new text shows** (debounce ≤ ~0.5s)
7. Upload a personal photo into the template's image block → it shows in canvas **and** preview (asset protocol path verified)
8. Repeat steps 2–7 for **Portfolio** and **Restaurant** — all three must feel finished out of the box
9. Start from **Blank** instead → empty canvas hint (from Phase 2) still shows
10. `npx vitest run` → generator golden test passes
11. Save & reopen a template project → assets, styles, tree all intact

## 6. Definition of Done

> **Phase 4 is done when:** every start path (blank or 3 templates) lands in a working, styled page; preview renders the generator's real output at 3 device widths with working mobile nav; edits propagate to preview in under half a second; and the generator is snapshot-tested. At this point LocalWeb is *visibly* a website builder — only export and polish remain.

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Images don't load in preview | The `resolveAsset` mapper (§2.1) exists precisely for this; verify `convertFileSrc` on one image before building the rest. |
| `srcdoc` + sandbox quirks (scripts/fonts blocked) | Start with `sandbox="allow-scripts"`; paste the console error to AI — srcdoc quirks are well-known and fixable in one prompt. |
| Templates drift from the data model | Factory functions return `BlockNode[]` — the **compiler** rejects invalid templates. Plus the generator golden test catches rendering drift. |
| Windows font smoothing makes scaled preview look blurry | Use `scale` steps of 0.05 max and device widths that usually fit (1280 on a 1080p screen is borderline — scale-to-fit handles it; note it as cosmetic only). |
| Template content feels generic | Spend a real afternoon on copy and sample images — this is product surface, not filler. |

## 8. Tips for building with AI (this phase)

1. Build the generator **before** the preview UI — then preview is "just an iframe" (one sitting).
2. Give AI the Phase-3 spec sheet for a block + ask for its `renderBlock` case — generator code is mechanical translation of the spec.
3. Ask AI for *"a vitest snapshot test around an unstable function"* and commit the snapshot — it guards the rest of the project for free.
4. For template trees, generate them **with the app itself**: drag the template page by hand in your editor, save the project, then convert that `project.json` tree into the template factory. WYSIWYG templates, zero imagination gap.
